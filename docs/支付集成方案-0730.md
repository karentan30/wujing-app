# 舞镜支付集成方案（¥9.9/一支舞 → 解锁并生成完整拆解卡）— 0730

> 产出：`_live/pay.py`（新模块，自包含）。本文档给主控把关后上 staging 集成用。
> **本轮未接任何明文生产密钥、未发起任何计费请求、未改线上 `/www/wujing-api/server.py`。**

## 0. 产品与履约（务必对齐，别照搬 Lumee 会员逻辑）

| 项 | 值 |
|---|---|
| 商品 | 一支舞的「完整拆解卡」（可下载、带水印） |
| 境内价 | **¥9.9**（env `WJ_DANCE_PRICE_CNY`，默认 9.9） |
| 海外价 | **$1.99**（env `WJ_DANCE_PRICE_USD`，默认 1.99；Stripe 按 USD 计价，见风险点） |
| 渠道 | 微信 NATIVE 扫码 / 支付宝当面付扫码 / 海外 Stripe Checkout |
| 履约 | 付款成功 → 该 `dance_id` 标记解锁 → 异步触发 `auto_decompose.run_decompose` 生成完整拆解卡 → 回写 `breakdown_status` → 前端轮询到 `completed` 后取卡 |
| 幂等键 | `out_trade_no`（订单号）；`orders.status` 原子翻转防重复履约 |

**它是「一支舞一单」，不是会员/订阅。** Lumee 的 `_apply_paid_order`（会员/鹿币/加油包/珍藏）逻辑全部弃用，只保留其签名/验签/统一下单/幂等模式。

## 1. 订单表（`orders`，同 wujing.db）

`pay.py` 的 `init_orders_table()` 幂等建表 + 存量补列：

```
orders(
  out_trade_no PRIMARY KEY, user_id, dance_id, amount, status,
  channel, currency, trade_no, breakdown_status, created_at, paid_at )
```

- `status`: pending / paid / failed
- `channel`: wechat / alipay / stripe
- `breakdown_status`: '' / queued / processing / completed / failed
- ⚠️ 现有生产 `orders` 表是「付费门骨架」建的（列有 id/product/amount/currency/channel/status/trade_no/consumed_at…），**缺 `dance_id` / `breakdown_status`**。`init_orders_table()` 已用 `ALTER TABLE ADD COLUMN`（幂等、不破坏存量）补上。上 staging 前先在 staging 库跑一次确认无冲突。
  - 注意：现有 free-quota 逻辑（server.py `/api/upload`、`/api/decompose`）往同一张 orders 表写 `product='free'` 占位行。本模块只按 `dance_id + status='paid'` 查解锁，不受 free 行干扰；两套逻辑共表但不冲突。

## 2. 路由怎么挂进 server.py

`server.py` 已经 `app.include_router(pay_router)`——但当前 import 的是 `payment`（生产上已有的 Stripe 骨架模块）。两种集成路径，**由主控二选一**：

**方案 A（推荐·并存）**：新增一行，让 pay.py 与现有 payment.py 并存（前缀不同不冲突：pay.py 用 `/api/pay/wechat|alipay|stripe/*`，旧骨架用 `/api/pay/checkout|webhook`）。
```python
from pay import router as dance_pay_router, init_orders_table as init_dance_orders
app.include_router(dance_pay_router)
# 启动处：
init_dance_orders()
```
> 若两个 router 都 `prefix="/api/pay"` 且有同名子路径会 405/冲突——本模块子路径（wechat/create、alipay/create、stripe/create、stripe/webhook、status、dance/{id}/unlocked）与旧骨架（checkout、webhook、wechat/create、alipay/create）**有重叠**（wechat/create、alipay/create）。上 staging 前主控确认：是替换旧骨架，还是把旧骨架的 wechat/alipay 桩删掉只留 pay.py。**建议：删掉旧 payment.py 里的 wechat/alipay 503 桩，统一走 pay.py。**

**方案 B（替换）**：把 server.py 里 `from payment import ...` 整体换成 `from pay import router as pay_router, init_orders_table`，删掉旧 payment.py。前提：确认旧 `check_analysis_access` / free-quota 门是否还要（server.py 的 `/api/upload`、`/api/decompose` 依赖它）——若要保留 free-quota，pay.py 需再补 `check_analysis_access` / `get_db`（当前 pay.py 已提供 `get_db`，未提供 `check_analysis_access`）。**因此方案 A 更省事、风险小。**

## 3. 前端怎么调（auth-pay.html 付款页）

所有请求带 `Authorization: Bearer <token>`（登录后拿的 JWT）。

**下单（三选一，按用户地区/选择）：**
```
POST /api/pay/wechat/create   body {"dance_id":"<did>"}  → {code_url}   前端 qrcode.js 生成二维码
POST /api/pay/alipay/create   body {"dance_id":"<did>"}  → {qr_code}    同上
POST /api/pay/stripe/create   body {"dance_id":"<did>"}  → {url}        window.location = url（跳 Stripe）
```

**轮询（每 3 秒，直到 paid 且 breakdown_status=completed）：**
```
GET /api/pay/status?out_trade_no=<oid>
  → {status:"pending|paid", breakdown_status:"queued|processing|completed|failed", dance_id}
```
- `status=paid` 且 `breakdown_status=completed` → 停止轮询，跳 `GET /api/decompose/{dance_id}` 取完整拆解卡渲染 + 显示「下载」按钮。
- `breakdown_status=failed` → 提示「拆解生成失败，请重新上传该舞」（已付款不重复扣，重试走重新生成，不重复下单）。

**门控下载（可选，防未付偷取完整卡）：**
```
GET /api/pay/dance/{dance_id}/unlocked → {unlocked:bool, breakdown_status}
```

**关键 UX**：Stripe 回跳 `success_url` 带 `?oid=<session_id>`——前端回到页后仍用轮询 `GET /api/pay/status` 兜底确认（webhook 可能比回跳慢）。异步等待处务必转圈+禁用按钮（铁律）。

写进 `/www/wujing-api/start.sh` 的 `export`，`env_loader.py` 自动读。缺任一渠道的 key → 该渠道 `/create` 返回 **503**，不崩、不 mock。

## 5. 回调（notify/webhook）URL — 必须公网 HTTPS

舞镜生产域名 `wujing.mylumee.app`（HK 服务器 47.242.80.65，Caddy 反代）：
- 微信：`https://wujing.mylumee.app/api/pay/wechat/notify`（商户后台配「支付回调 URL」）
- 支付宝：`https://wujing.mylumee.app/api/pay/alipay/notify`（下单已带 notify_url，无需后台配）
- Stripe：`https://wujing.mylumee.app/api/pay/stripe/webhook`（Dashboard → Webhooks 建 endpoint，监听 `checkout.session.completed`，拿 `whsec_`）

> ⚠️ 三个 notify 路由**无 Authorization 门**（回调来自支付平台，不带用户 token），安全靠**验签**：微信 MD5、支付宝 RSA2、Stripe HMAC-SHA256。Caddy 层不要给 `/api/pay/*/notify`、`/api/pay/stripe/webhook` 加鉴权中间件，否则平台回调被 401。

## 6. 安全/正确性要点（已在 pay.py 落实）

- **验签**：三渠道回调全部服务端验签，绝不信前端传入结果。Stripe 额外查 `payment_status=='paid'` + 防重放（timestamp tolerance 300s）。
- **金额校验**：回调金额必须 == 本地下单金额（微信按分、支付宝/Stripe 按元），不符即拒并 log。
- **幂等**：`_mark_paid_and_fulfill` 在 `_ORDER_LOCK` 内 `UPDATE ... WHERE status!='paid'` + rowcount 判定，仅本次翻 paid 的调用投递履约；重复回调命中 `status=='paid'` 早返回。
- **订单锁**：进程内 `threading.Lock` 串行化「翻 paid → 履约投递」临界区（履约本身异步，锁内只做轻量 DB 写 + 投递，不阻塞）。
- **履约失败不吞款**：源视频缺失或 run_decompose 失败 → `breakdown_status=failed`，前端提示重试（重生成不重复扣款）。

# 7. Staging 测试方案（不碰真钱测通「下单→支付→回调→解锁出卡」）

前提：staging 后端跑 pay.py（方案 A 挂好），公网 HTTPS 回调可达（wujing.mylumee.app 或 staging 子域）。**先在 staging 独立 wujing.db 上跑，别碰生产库。**

## 7.0 前置：建一支「已上传但未付费」的舞（拿 dance_id）
登录拿 token → `POST /api/decompose`（免费额度那次上传）→ 拿到 `decompose_id`（这就是 `dance_id`，`data/<id>/input.mp4` 会存在，履约生成拆解卡靠它）。

## 7.1 无 key 冒烟（零成本，先跑）
不配任何支付 key，直接打三个 create：
```
POST /api/pay/wechat/create  {"dance_id":"<did>"} → 期望 503 "微信支付暂未开放"
POST /api/pay/alipay/create  {"dance_id":"<did>"} → 期望 503
POST /api/pay/stripe/create  {"dance_id":"<did>"} → 期望 503
GET  /api/health → ok（确认挂 router 没崩）
```
验证「缺 key 不崩、不 mock」。

## 7.2 Stripe 测试模式（最容易全链路测通，零真钱）
1. start.sh 填 `STRIPE_SECRET_KEY=sk_test_…` + webhook endpoint（test）拿的 `STRIPE_WEBHOOK_SECRET=whsec_…`，restart。
2. Dashboard → Webhooks 建 endpoint URL = `https://<staging>/api/pay/stripe/webhook`，监听 `checkout.session.completed`。
3. `POST /api/pay/stripe/create {"dance_id":"<did>"}` → 拿 `url`，浏览器打开，用 Stripe 测试卡 `4242 4242 4242 4242`（任意未来日期/CVC）付款。
4. webhook 回来 → `GET /api/pay/status?out_trade_no=<oid>`：应 `status=paid`，`breakdown_status` 从 queued→processing→completed。
5. `completed` 后 `GET /api/decompose/<did>` 应返回完整拆解卡；`GET /api/pay/dance/<did>/unlocked` 应 `unlocked=true`。
6. **幂等测试**：用 Stripe CLI `stripe events resend <evt_id>` 或 Dashboard 重发同一 webhook → 订单仍 paid、拆解卡**不重复生成**（breakdown_status 不回退）。
7. **验签测试**：手动 POST 一个假 body 到 webhook（错的 Stripe-Signature）→ 期望 400 invalid signature。

> Stripe CLI 本地转发（无需公网）：`stripe listen --forward-to localhost:3006/api/pay/stripe/webhook`，它给你一个临时 whsec，填进 env 即可本机测。

## 7.3 支付宝沙箱（零真钱）
1. 支付宝开放平台「沙箱环境」拿沙箱 APPID + 沙箱应用私钥 + 沙箱支付宝公钥，`ALIPAY_GATEWAY=https://openapi-sandbox.dl.alipaydev.com/gateway.do`。
2. `pip install python-alipay-sdk`（staging venv）。
3. `POST /api/pay/alipay/create {"dance_id":"<did>"}` → 拿 `qr_code` → 用**沙箱买家账号**（沙箱钱包 App 扫）或沙箱 SDK 模拟支付。
4. 沙箱异步 notify 回 `/api/pay/alipay/notify` → 轮询 `GET /api/pay/status` 应 paid + 出卡。
5. 兜底测：若沙箱 notify 到不了，轮询 `GET /api/pay/alipay/query?out_trade_no=<oid>` 会主动 `trade.query` 拉回 paid。

## 7.4 微信（沙箱受限，谨慎）
微信支付 v2 沙箱能力有限（沙箱只对部分接口开放、且要单独 sandbox signkey），**真扫码需企业商户号**。建议：
- **staging 阶段先只用 1 分钱真单验真链路**：`WJ_DANCE_PRICE_CNY=0.01`，配真商户号，真扫码支付 1 分 → 验回调/幂等/出卡 → 立即在商户后台退款。总成本 1 分。
- 或先跳过微信真测，靠 Stripe/支付宝沙箱验通用链路（notify→翻 paid→履约 的代码路径三渠道共用 `_mark_paid_and_fulfill`，Stripe/支付宝测通即证明该核心逻辑正确）。

## 7.5 通用断言清单（每渠道都过）
- [ ] 下单写一条 pending 订单（金额/币种/channel/dance_id 正确）
- [ ] 回调验签失败 → 拒（返回 fail/400），订单仍 pending
- [ ] 回调金额被改（篡改 total_fee/total_amount）→ 拒，订单仍 pending
- [ ] 正常回调 → paid + breakdown_status 走完到 completed + decompose.json 存在
- [ ] 重复回调 2 次 → 仍单次履约（拆解卡不重复生成、无第二条 paid）
- [ ] 源视频缺失时付款 → breakdown_status=failed，不吞款语义（前端可重试重生成）
- [ ] `/api/pay/status` 无 token → 401；带 token 正常
- [ ] 全绿后 Stripe 换 `sk_live_`、微信/支付宝换生产密钥上真号（由主控把关）
