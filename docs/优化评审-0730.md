# 舞镜 · 任意舞自动拆解系统 · 优化评审 & 路线图（0730）

> 评审范围：`auto_decompose.py`（引擎）/ `pose_angles.py`（MediaPipe 姿态）/ `server.py`（FastAPI）。
> 立场：只读分析，不改代码。所有结论对着代码行号，给具体数字/方案。
> 结论先行 →「最该先做的 3 件」在文末。

---

## 0. 一句话总评

系统**能跑、产物齐、兜底干净**（`run_decompose` 全程 try 包住，失败不留半成品，QA 28/28 合理）。
但有 **3 个静默烧钱/掉体验的坑**藏在正常路径里，规模化前必须堵：
1. `/api/generate-bg` 每次调用豆包 Seedream 生图（`server.py:351`），**只有登录门没有额度门** → 最大烧钱漏洞（记忆里已记「疑 seedream 批量烧 300+」，这就是入口）。
2. `/api/decompose` 上传**零文件校验**（`server.py:387` 直接 `await video.read()` 全量进内存 + 落盘）→ 可传任意大文件/非视频，OOM + 磁盘打爆。
3. `vision_coach` 的 **genre 判定驱动整支的风格分类**，但 K-pop 暗场群舞 pose 检出仅 43%，点评在「无真实角度」时会退化成它自己明令禁止的空泛套话——护城河在最需要的场景反而失效。

其余是「够用 v1，规模化要还的债」：固定分段 vs 真节拍、mpvenv 子进程冷启开销、SQLite 并发、无存储清理。

## 1. 拆解质量：固定等分 vs 真节拍

**问题**
`auto_decompose.py:194` `n = round(dur/3.3)` 固定按 3.3s 等分，`bpm` 恒为 `None`（:256）。
后果：等分点几乎永远**踩不在真实八拍的第一拍上**。一支 128BPM 的舞，一个八拍 = 3.75s，用 3.3s 切会持续相位漂移，到第 5 段偏差可达半个八拍——胶片条的「起势/亮相」帧会切在动作中段，vision 描述的 `name`（起势/旋身/亮相）跟着错位。这是**质量天花板**，不是 bug 但直接压产物专业度。

**建议（按性价比）**
- **A（低成本·先做）**：`librosa.beat.beat_track` 只取 `tempo` + `beat_times`，按「每 8 拍一段」切。librosa 纯 CPU、一支 20-40s 视频抽音频算节拍 <2s。装在 mpvenv 或再开一个 venv（librosa 也拖 numpy，别塞主服务）。段边界对齐到最近的 downbeat。
- **B（vision 更省更准）**：现在**每段一次 vision describe**（n 段 = n 次调用，:219）。可改成**一次多图批量**：把 n 段的中帧拼成一张 grid（或一次 input 塞多图），让 vision 一次返回 n 段 JSON 数组。豆包按图数计费但省了 n-1 次「请求 overhead + 思考关不掉的隐形 token」，实测通常能省 30-40% describe 成本，且跨段命名更一致（模型看到全局，不会把两个「亮相」都叫亮相）。
- **C**：describe 的 `full` 字段被 `[:14]` 硬截（:107），会把「手臂经体前画弧上举至头顶」截成半句显示。改为让模型直接产出 ≤14 字，别截断。

**预期收益**：八拍对齐正确率从「碰运气」→ 稳定；describe 成本 -30%。 **改动量**：A 中（加依赖+切段逻辑），B 中（重构 describe 为批量），C 小。

## 2. 成本：¥0.06/支构成 & 规模化

**现状拆解（每支）**
- vision describe：n 段 × 1 次，n=5~10 → **5~10 次**（:219）
- vision coach：1 次，塞 5 帧（:115 `[:5]`）
- DeepSeek story：1 次（:159）
- 合计 **7~12 次 LLM 调用**。¥0.06 是乐观值（5 段），10 段的舞实际接近 **¥0.10+**。

**能省的点**
1. **describe 批量化**（见 §1-B）：n 次 → 1 次，最大杠杆。
2. **图尺寸已优化**（`_grab` scale=360、q:v 3，:42）—— 合理，别再压，再小 vision 认不清手型。
3. **coach 与 describe 复用帧**：coach 另取 5 帧（:238 `pick`），但这 5 帧其实是 describe 已看过的中帧子集，图没重复抽是对的；但**两次调用看的是同一批图**，可考虑合并成一次「describe + coach」大 prompt（省 1 次），代价是 prompt 变复杂、JSON 更易崩。**建议先不合**，稳定性优先。
4. **缓存**：同一用户重传同一支舞（reupload/重试）没有去重。可对 `input.mp4` 算 md5，命中直接返回旧 `decompose.json`。防重试烧钱。

**规模化 1 万支/天估算**
- LLM：1 万 × ¥0.08 均值 ≈ **¥800/天 ≈ ¥2.4 万/月**。可控，但**没有全局预算熔断**——豆包/DeepSeek 挂了或被刷，账单无上限。
- **风险点（比 LLM 更凶）**：
  - `/api/generate-bg`（§8）无额度门，被刷 = Seedream 生图烧钱无底。
  - 存储：每支存 input.mp4（1-5MB）+ n 段 clips（各百 KB~MB，:228 每段真编码一次）+ ~5n 帧图。**一支约 5-20MB**。1 万/天 = **50-200GB/天**，30 天 = 数 TB。**当前无任何清理逻辑**（PRD B-10 才规划「N 天清原片」，未实现）。这是规模化第一个爆的东西。

**建议**：describe 批量（-30% LLM）+ generate-bg 上额度门 + 全局日预算计数器（超阈值拒新任务并告警）+ 落地存储 TTL 清理（免费用户 7 天清原片和 clips，只留 decompose.json + 缩略帧）。
**预期收益**：LLM -30%、堵住无底洞、磁盘从「必炸」→ 稳态。 **改动量**：中。

## 3. 性能 / 延迟

**瓶颈定位（一支 20-40s 视频，串行看代码流）**
1. **ffmpeg 抽帧**：n 段 × 5 帧 = 25~50 次**独立 ffmpeg 进程**（:202-206，每帧一次 `-ss` seek）。每次进程冷启 + seek，累计可达 5-15s。**这是最大且最易修的瓶颈。**
2. **MediaPipe 子进程**（:209）：`_run_pose` 一次子进程，但 **mpvenv 冷启 + 模型加载**（pose_landmarker.task）每次都重来。加载 MediaPipe + 模型通常 2-4s，纯推理 n 帧很快。子进程一次批量是对的（:5 注释「模型只加载一次」），但**每次上传都重新冷启一个 Python 进程**。
3. **vision describe**：已 4 线程并行（:219 `max_workers=4`），10 段要跑 3 批，每次网络往返 1-3s → 3-9s。
4. **clips 切片**：n 段各真编码一次（:228 libx264 veryfast），10 段 = 10 次编码，可达 5-10s。
5. **story + coach**：串行在最后（:231, :241），各 1-3s。

**总延迟粗估**：25-45s（QA 里轮询 50×3s=150s 上限也印证不是秒级）。

**压缩方案（按 ROI）**
- **抽帧合并**：用**单次 ffmpeg** 带 `select` filter 或 `fps` 一次抽全部帧到 `p%03d.jpg`，而不是 25-50 次进程。**这一项可砍掉大部分 ffmpeg 时间**（进程启动 × 数十次 → 1 次）。最高 ROI。
- **clips 切片改无重编码**：分段切片用 `-c copy`（关键帧对齐容忍些）代替 libx264 重编码，10 次编码 → 近乎瞬间。慢放/镜像已是前端 `playbackRate`/`scaleX`（记忆确认），分段 clip 根本不需要重编码。
- **pose 常驻**：把 pose_angles 从「每次 fork 子进程」改成**常驻 worker**（mpvenv 起一个小 HTTP/socket 服务，模型加载一次常驻），主服务发帧路径过去。省每次 2-4s 冷启。规模化必做。
- **describe + pose + 抽帧流水线化**：抽完帧就能并行发 pose 和 vision，别等 pose 回来再 describe（当前 :209 pose 完 → :219 describe，其实无依赖可并行）。
**预期收益**：单支 25-45s → **10-18s**。 **改动量**：抽帧合并/`-c copy` 小且高收益；pose 常驻 中。

## 4. 姿态角度：K-pop 暗场群舞检出率（43%）

**根因确认**（已知限制说得对）：不是暗，是**多人剪影 + num_poses=1**。`pose_angles.py:46` `num_poses=1` 只找一个人，群舞里 MediaPipe 要么锁错人要么放弃。现有「提亮 1.6×+45」重试（:57）对**多人剪影无效**——提亮不能把 5 个人变成 1 个人。

**真正能救的方案（按投入排序）**
1. **产品侧引导（零成本·先做）**：上传页明确提示「**单人、正面、光线清晰**的视频角度分析最准」，并在结果里当 pose 全 miss 时给友好文案「这支是群舞/暗场，角度测量跳过，其余卡片正常」。现在是静默不显示（`_run_pose` 失败返 `{}`），用户不知道为什么没角度。**期望管理 > 硬救**。
2. **多人检测 + 选主舞者**：`num_poses=3~5`，然后按「bbox 面积最大 / 最居中 / visibility 最高」选主体。MediaPipe 支持多 pose，改一个参数 + 一段选人逻辑。能把「群舞里挑出前排主舞者」的场景救回来。**中等改动、直接提检出率。**
3. **裁剪主舞者再测**：先跑一次粗检测拿到主体 bbox，裁剪放大后重测——对「主舞者只占画面 1/5」的远景群舞有效。
4. **换 heavy 模型**：`pose_landmarker.task` 有 lite/full/heavy 三档，暗场低对比 heavy 检出率更高，代价是推理慢 2-3×（配合 §3 pose 常驻就不心疼）。**性价比中。**
5. **别硬救 K-pop 群舞**：诚实讲，官方 MV 的暗场群舞剪影，任何单目 2D pose 都难。产品定位应引导用户传**自己跳的单人练习视频**（这本来就是核心用例——用户是来纠自己的错的，不是分析 MV）。**方案 1 + 2 组合即可覆盖 90% 真实用例。**

**预期收益**：单人清晰视频本就 100%；群舞场景检出从 43% → 70%+（选主舞者）；体验上「静默没角度」→「明确告知」。 **改动量**：1 小、2 中、4 小（换模型文件）。

## 5. 健壮性 / 边界

对着 `run_decompose` 逐个边界看：

| 边界 | 当前行为 | 风险 | 建议 |
|---|---|---|---|
| 超短（<1s）| `n=max(5,...)`=5 段（:194），每段 <0.2s | 5 帧全抽在同一瞬间，切片近乎空 | 时长 <3s 直接拒「视频太短，至少 3 秒」 |
| 超长（>3min）| `n=min(10,...)`=10 段封顶 | 10 段覆盖 5min 舞 = 每段 30s，胶片条完全失去意义 | >90s 时提示「只拆前 90s」或按真节拍分更多段 |
| 无音频 | `_dur` 靠 ffprobe format，不看音轨；describe 不依赖音频 → OK | 上 librosa 后会崩（无音频轨） | librosa 前先探音轨，无则回落固定分段 |
| 竖屏/横屏 | `scale=360:-1`（:42）保比例 → OK | pose 归一化坐标不受影响 → OK | 无需改 |
| 无人视频（传了张风景/宠物）| pose 全 miss + vision 硬答（会瞎编「起势」）| **产物看着正常实则全错**，用户被误导 | vision describe 加「若画面无人物跳舞，name 返回 '无人物'」，检出 >50% 段无人物 → 标记 low-confidence |
| 模糊视频 | vision 照答、pose 低 visibility 但仍返角度 | 角度不可信但照显示 | pose 返回的 `visibility`（:67 已算）没用上！低于阈值（如 <0.5）应不显示该段角度 |
| 损坏文件 | `_dur<=0` → raise → status=failed（:192）✅ | 兜底 OK | 保持 |

**最重要一条**：`pose_angles.py:67` **已经算了 visibility 但 auto_decompose 完全没用**（:70 只取 `angles`）。低置信度的角度照样喂给点评当「客观真数字」——这会**污染护城河**（拿不可信的 68° 去纠错）。**必须按 visibility 过滤。**

**预期收益**：堵住「无人/模糊也一本正经出错角度」的信任崩塌。 **改动量**：小（加时长门 + visibility 阈值 + describe 无人物分支）。

## 6. 架构

- **mpvenv 子进程**：每次上传 fork 一个 Python 冷启 + 加载模型（§3-3）。单机低并发能忍，规模化必改常驻 worker。**当前设计（独立 venv 避 numpy 冲突）是对的**，问题只在「进程生命周期」。
- **并发上传**：`threading.Thread(daemon=True)`（:404）每个上传起一个线程，**无队列、无并发上限**。10 个人同时传 → 10 个 ffmpeg 洪流 + 10 个 mpvenv 进程 + 40 个 vision 线程，单机 CPU/内存瞬间打满，互相拖慢甚至 OOM。**需要一个有界任务队列**（如 `concurrent.futures` 全局池 max_workers=2-4，或 Celery/RQ）。规模化第一硬约束。
- **`await video.read()` 全量进内存**（:387/:193）：大文件直接 OOM。应流式落盘（分块写）+ 大小上限（见 §8）。
- **存储**：无 TTL、无清理（§2）。且 `data/<id>/` 平铺，1 万/天后单目录几十万子目录，`os.listdir`/inode 都会退化。建议按日期分桶 `data/YYYYMMDD/<id>/`。
- **数据库**：`orders` 表用 free 占位行计免费额度（:218/:392），每次 decompose + 每次 upload 都 INSERT 一行。SQLite（看 models 用法像 sqlite）**写并发差**，高 QPS 下 `database is locked` 会频发。规模化迁 Postgres。
**预期收益**：从「单机能演示」→「能扛真流量」。 **改动量**：队列 中、流式落盘 小、存储分桶 小、DB 迁移 大（不急）。

## 7. 产品体验

- **加载时长感知**：拆解 10-45s，前端只有 processing/completed 二态（QA 轮询证实）。**用户盯着转圈 40s 会以为坏了**（记忆里 Lumee「加载反馈铁律」——异步等待必须有进度感）。建议 `decompose.json` 写**阶段进度**（`stage: "抽帧"/"AI描述 3/8 段"/"生成故事卡"），前端显示步骤条。低成本、大幅降跳出。
- **错误提示**：失败只写 `traceback[-500:]` 到 json（:261），前端拿到 status=failed **没有人话原因**。用户不知道是「视频太短」还是「服务器忙」。应映射成用户可读原因（太短/非视频/太大/服务器繁忙请重试）。
- **免费额度门**：`check_analysis_access` 异常时 `_access={"allowed":True}` **fail-open**（:378-379）——付费检查一崩，所有人免费畅用。安全上应 fail-closed 或至少限流。且免费计数靠往 orders 表插 free 行（:392），**INSERT 失败被 except 静默吞掉**（:401）→ 计数丢失 = 白嫖。防刷有洞。
- **防刷**：目前只有「登录 + 每月 N 次免费」。没有**频率限制**（一个账号 1 秒连传 100 次全部起线程）。建议加 per-user 速率限制（如 1 次/30s 在处理中不许再传）。

**预期收益**：跳出率↓、白嫖↓、错误可自助。 **改动量**：进度阶段 中、错误映射 小、fail-closed 小、限流 小。

## 8. 安全（最紧急的一节）

按严重度：

1. 🔴 **`/api/generate-bg` 无额度门**（`server.py:340`）：只有 `get_current_user` 登录门，**任何登录用户可无限调用豆包 Seedream 生图**（:351，720x1280 一张成本远高于文字 LLM）。这与记忆里「豆包莫名烧 300+、/api/generate-bg 无鉴权=烧钱漏洞要堵」**完全吻合**——它有登录鉴权但**没有额度/频率门**，本质仍是烧钱洞。**必须上额度门 + 频率限制，或直接下线（前端若不用就删）。**
2. 🔴 **上传零校验**（:387, :193）：无 `content-type` 检查、无大小上限、无时长上限、全量进内存。可传 2GB 文件 OOM，或传伪装成 mp4 的任意文件。**加：大小上限（如 100MB）+ 流式落盘 + 落盘后 ffprobe 验真是视频 + 时长上限。**
3. 🟡 **path 拼接**：`/clip/{name}` 和 `/frame/{name}` 已做 `isalnum()+_` 过滤（:421/:433）✅，`did` 直接进 `os.path.join` 但只用于查已存在文件、且 `get_decompose` 有 user_id 校验（:414）——**但 `/clip` 和 `/frame` 两个端点完全没有鉴权也没有 user_id 校验**（:418/:430）！任何人知道 `did`（UUID）就能拉别人的原片和帧图。UUID 难猜但**分享/日志泄露 did 即越权看原片**。建议这两个端点也校验归属，或改签名 URL。
4. 🟡 **fail-open 额度门**（§7）：付费检查异常即放行。
5. 🟢 **CORS** 白名单明确（:20）✅；越权 `/api/decompose/{id}` 有 403（:414）✅。

**预期收益**：堵住两个烧钱/OOM 洞 + 一个越权看原片洞。 **改动量**：generate-bg 额度门 小、上传校验 中、clip/frame 鉴权 小。
